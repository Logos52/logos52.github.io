# Scope a bot like a job description

A bot works best with one job, written down the way you would describe a role for a new teammate. The description says what the bot owns and what it doesn't, holds the standing rules it follows every time, and points to the materials and access it needs to be good at that job. Written well, the description stays short and general, so it keeps working as the bot takes on new tasks within its lane.

**Scope.** This draws on how speakers at the Grok Bot Galaxy livestream scoped their bots over three days, for slides, marketing, sales, customers and engineering. It applies to any bot whose description you can edit.

<div class="callout">

<b>At a glance</b>

1. List the work you need done, then group it into domains.
2. Give each bot one job and write its lane like a job description.
3. Put the rules it should follow every time into its description.
4. Give it the materials and access to be an expert at that job.
5. Let it widen its scope once you trust it.
6. Keep the description at the level of principles.

</div>

## Why it works

A bot's description works almost like a system prompt, which some people call the bot's soul, and it affects how the bot works. One speaker described scoping as identifying a new teammate you need help from, and said tight scoping keeps each bot specialized enough to get its piece of work done. That, the speaker said, is how you get the most efficiency out of a team of bots. Another speaker gives a bot very detailed instructions, because that makes its work more consistent.

## The method

1. **Inventory the work first.** Asked how to set up roles for bots, one speaker said to start by listing everything you need done, so that you can group it. That speaker groups bots by domain, such as finance, dealing with customers or marketing.
2. **Give each bot one job, written like a job description.** Know the swim lanes, roles and responsibilities, and scope the bot tightly enough that it can specialize. Another speaker put it as "have one bot with one job", whether a chief of staff delegates to them or you talk to each bot yourself. In one demo, the description the bot-making bot wrote also specified one job, so that the bot wouldn't try to do everything.
3. **Write standing rules into the description.** One presenter's slide bot has very explicit instructions in its description on how to edit an existing deck: use a particular font with particular colors, and send back a screenshot of each slide once it is done. Because the bot already has that predefined set of things to do, going back and forth with it is easier. A description can also set the voice the bot uses with you.
4. **Give it what an expert needs.** Treat bots as team members you are onboarding: make them an expert in their field and give them all the relevant information and materials to be great at that job. Trust starts with access, such as connecting the bot to your Slack and email. You can then ask it to study that context and tell you what job it can take off your plate.
5. **Let the scope grow with trust.** One speaker's bots start with a specific domain and expand their scope as that speaker brings them questions outside it.
6. **Keep the description at the level of principles.** Looking at a description that had become too specific, one speaker noted that a rule or skill written right after one problem tends to absorb that session's details, which makes it less reusable. [[wiki/Working with Agents/Scope a bot like a job description|Set up a first engineering bot]] shows one being rewritten as principles.

### A prompt to copy

> Create a bot whose one job is <job>. Write its description like a job description for a new teammate: what it owns, what it leaves to other bots, the rules it follows every time (<rules>), and the materials and access it needs to be an expert. Keep the description to principles, not details from one task.

## Signals and failure points

| What you notice | What it means | What to do |
|---|---|---|
| A bot tries to do everything | It has no single job | Split the work and give each bot one job |
| Its output varies from run to run | Its standing rules aren't in the description | Write explicit rules into the description |
| It can't do its job well | It lacks materials or access | Give it what an expert in that role would need |
| Its description reads like notes from one session | It has become too specific | Rewrite it as principles |

Scoped this way, each bot holds one job, with its own rules and materials, and a short description you can keep editing as the work changes.

## Organize a fleet of bots

# Organize a fleet of bots

A handful of bots tangle quickly when you talk to each one separately and each keeps its own version of the facts. The fix is to give the fleet a shape: one bot you talk to that hands out the work, other bots with one job each, a group chat for each project, and one shared document that every bot keeps up to date. A regular checkup of the whole fleet then catches the bots that keep making the same mistake.

**Scope.** This draws on [Lauren](https://www.youtube.com/watch?v=xZ5TEaleUdg)'s own fleet, shown in a video tour of the bots she uses, together with the bot teams that speakers built and ran during the three days of the Grok Bot Galaxy livestream. It fits anyone running more than a few bots, for work or at home.

<div class="callout">

<b>At a glance</b>

1. Talk to one chief of staff bot, and let it hand work to the others.
2. Give every other bot one job and a name.
3. Put the bots working on one project into a group chat.
4. Keep one shared document as the source of truth, and tell every bot to keep it updated.
5. Check the fleet on a schedule for repeated mistakes and wasteful routines.

</div>

## Why it works

One livestream speaker compared this shape to a coding agent, where an orchestrator fans work out to others. You then interact with the orchestrator rather than with each bot, and you stay in one thread of context. A shared document gives every bot the same facts, and on the livestream one speaker called such documents the way for bots to work with other bots and with the company's context. For engineering work the codebase already plays that role, as the best source of context and memory, but for many operational tasks it helps to write docs.

## The method

1. **Make one bot the front door.** A chief of staff bot takes your requests and passes them on, and it can create new bots too. Asked to spin up three bots that would help, a chief of staff typically creates something like an inbox manager and a scheduler. In [Lauren](https://www.youtube.com/watch?v=xZ5TEaleUdg)'s fleet she mostly talks to her chief of staff, which talks to an engineering lead bot whose job is to break tasks down and delegate rather than do the work.
2. **Give each other bot one job and a name.** When a bot-making bot drew up a new bot on the livestream, it gave the bot one job so that it was a specialist and not a bot that tries to do everything. [Lauren](https://www.youtube.com/watch?v=xZ5TEaleUdg)'s bot-making bot gives her bots food names.
3. **Group bots by project.** One speaker works out each bot's swim lane and then puts the bots for one initiative, such as website conversion, into a group chat where they work on it together. Initiatives start and stop, while the bots themselves are always on and keep getting better. In the same video as [Lauren](https://www.youtube.com/watch?v=xZ5TEaleUdg), the other presenter puts three bots with different roles, such as product and design, into a single group chat so they can develop ideas with one another.
4. **Keep one shared document as the source of truth.** One speaker said they would tell their bot-making bot to tell the whole team that the shared document is the source of truth, and that every bot should keep it updated. By the last day, the team's shared documents held a task board, the database schema, the game's rules and a launch checklist written live. On screen, a bot that could not reach its page stalled mid-demo, so check that every bot can open the document.
5. **Check the fleet on a schedule.** [Lauren](https://www.youtube.com/watch?v=xZ5TEaleUdg)'s bot-making bot runs a fleet checkup that looks through all of her bots and their chat transcripts for a bot that keeps doing something it shouldn't. For each one it proposes a fix, such as a new skill, a new bot or a changed routine. It also reviews routines for waste, because a bot that wakes every 10 minutes burns usage. One livestream speaker runs routines only once or twice a day, finding more frequent ones noisy.

### A prompt to copy

> You are my chief of staff. Hand each request to the bot whose one job fits it, or ask the bot-making bot to create one if none does. Tell every bot that our shared document is the source of truth and that they must keep it updated. On a regular schedule (the sources give no cadence), read the bots' transcripts and routines, and tell me which bot keeps repeating a mistake and which routine wakes up more often than it needs to.

## Signals and failure points

| What you notice | What it means | What to do |
|---|---|---|
| You open every bot's thread to keep up | There is no front door | Route requests through one chief of staff |
| Two bots give different answers about the same fact | Each keeps its own version | Point both at the shared document |
| A bot stalls on a page it can't open | Its connection to the document is broken | Check access before relying on it |
| A bot keeps making the same mistake | Nobody checks the fleet | Add a scheduled checkup |

With one front door, single-job bots, a group chat per project and one shared document, a fleet behaves like a small team working from one set of notes, and the checkup keeps it that way as it grows.

## How other people staff their bot fleets

# How other people staff their bot fleets

> Not yet reviewed by Wedge.

Grouped by how they are built, the public fleets fall into four shapes, a working grouping rather than one any source makes. The most common puts a chief of staff bot on top, which takes the owner's requests and hands each one to a bot with a single job. Marketing and sales teams often chain bots instead, so each bot finishes its step and triggers the next. Companies also build shared team bots that a whole function uses, and many fleets include a bot whose job is to build, rewrite and audit the other bots. A catalogue of 149 publicly described bots, 117 of them confirmed by a source link, has marketing as its biggest group with 20 bots, then sales with 15 bots and engineering with 14 bots. About half of those bots act when someone talks to them, and about a third run on a schedule. The official setup advice points the same way, starting with the smallest roster that works and adding a bot only when a job has become a stable specialty.

## A chief of staff over one-job specialists

Most fleets that individuals have shown in public follow this shape, with the owner talking to one bot and that bot routing the work.

1. An engineer runs a work fleet. She talks to a chief of staff, which passes coding work to an engineering lead bot whose standing instruction is never to do work itself and always to delegate. The lead hands work to three or four engineer bots, and those engineer bots run Cursor cloud agents. For a big project the chief of staff first plans the phases in a Notion document.
2. One creator runs eleven bots. A chief bot handles email and delegates, and a separate bot builds new bots and improves the existing ones. The rest plan the week, find video ideas, write scripts, track website traffic and find trending posts on X. Others sell things, watch flight prices, find family activities, keep up with school emails and errands, track workouts and clean up files and subscriptions.
3. Another creator runs thirty or so agents. One chief bot sweeps six inboxes and Slack and coordinates the rest. Their jobs include printing a family newspaper for the children, closing the queue of code changes, monitoring security controls, customer support, auditing subscriptions and personal shopping.
4. A twenty-two-bot fleet is split by department and modelled on a human company. On the personal side are bots for health, travel and wardrobe, and the business side has social media and revenue bots and a chief of staff. A bot-making bot creates the others and keeps an organization chart.
5. The official work and product guides each show a fleet. In the work guide an inbox manager, a calendar assistant and an intelligence scout all report to one boss bot. The product guide adds an engineering manager over five engineer bots, a data analyst, a product manager bot and a recruiter, and every bot reads one shared attention list as its filter.

## Chains that hand work down a line

When each step's output is the next step's input, teams wire bots in a line so that one bot finishing wakes the next.

1. A marketing workshop's video description lists a chain of bots. A trend-spotting bot feeds an event-planning bot, then an event-page bot, an attendee finder, an outreach bot and an approvals bot. Bots that need each other share a group chat, and outside email stays a draft.
2. The official marketing team has six bots. A market researcher feeds a product marketer, who feeds a performance marketer and a website operations bot, and an analyst reads the results. A project manager bot runs the handoffs.
3. The official Founder Mode sales team has nine bots. A chief of staff sends an 8 AM list and sits over outreach, selling, inbox, insights, product, stock, content and social bots. The social bot passes warm leads to outreach, and the inbox bot passes what customers say to insights, which passes it to product.
4. The official recruiting team has four bots. One bot sources candidates overnight, one writes a note before each interview, one turns weak points into first-call questions and one drafts feedback from interview transcripts.
5. A video creator runs a small team. A news bot sends a daily digest, a script bot turns that research into scripts and an expenses bot files receipts, and the whole team holds a daily standup in a group chat.

## Shared bots for a whole team

Some companies build a bot once and share it, so everyone in a function works with the same bot. One field engineer estimated that about 90% of the bots in his company are team bots.

1. A sales team shares a set of bots. An account intelligence bot prepares reps for calls, reads call transcripts afterwards and drafts follow-ups. A quote bot builds pricing proposals and order forms, shows a preview and asks before it changes the sales database, then sends exceptions to a deal bot. The deal bot handles unusual terms and discounts and stamps each approval with the decision, the reason and the person responsible. A competitive intelligence bot and a sales training bot sit beside them.
2. One Galaxy livestream host has team bots for marketing review, social media review and brand design, shared with colleagues through Slack, where some people own a bot and others only use it.

## Bots that build and check the fleet

As fleets grow, owners add a bot that looks after the other bots. The engineer's bot-maker designs new bots and audits the fleet on a schedule, with a transcript check every weekday morning and a routine check every Monday, and it proposes changes for her to pick from. Her release flow chains bots too. A release manager bot asks contributors for objections, starts a build and sends a swarm of ten or more agents to test it, then calls an engineer bot to triage and fix what they find. A daily loop takes feedback from Slack, has a cloud agent reproduce the bug and fix it, tests the fix and merges it after an hour unless she objects.

## Set up a first engineering bot

# Set up a first engineering bot

In [Lauren](https://x.com/poteto/status/2094457600259842065)'s setup, an engineering bot doesn't write the code itself. Its job is to hand coding tasks to cloud agents, watch over them and check their work, which keeps the bot free and its context clean. Setting one up takes a short brief spoken to the bot that makes your bots, a check that it understood, a place for the engineering context to live, and a habit of turning its description into principles once it starts collecting narrow rules.

**Scope.** This follows [Lauren](https://x.com/poteto/status/2094457600259842065)'s practice of treating bots as coordinators of cloud agents, together with how speakers at the Grok Bot Galaxy livestream set up engineering bots for a game built live over three days. It fits anyone with a repository, cloud agents and a bot that can create other bots.

<div class="callout">

<b>At a glance</b>

1. Decide which bot you will talk to, and have it or your bot-making bot create the engineering bot.
2. Give it one job: spawn cloud agents, supervise them and check their work.
3. Ask it to restate the brief in its own words before it starts.
4. Give it the context it needs, and somewhere to keep the engineering context.
5. Add a reviewer when pull requests get too big to read.
6. When its description fills with narrow rules, rewrite it as principles.

</div>

## Why it works

[Lauren](https://x.com/poteto/status/2094457600259842065) tells her bot to start a cloud agent instead of writing the code itself, because that frees the bot for other tasks and keeps its context window clear. She thinks of her bots as coordinators that manage and oversee cloud agents, and each cloud agent gets its own machine, so the bot's computer stays free as well. On the livestream, a speaker explained splitting work across bots the same way: each bot owns its own context and becomes a bit of a specialist.

## The method

1. **Start from the bot you talk to.** On the first day of the livestream, one speaker asked their bot-making bot to turn their main bot into a chief of staff and planned to mostly talk to it. The next day a speaker explained that you can ask the bot-making bot directly or have your chief of staff ask it. Which to use depends on which bot holds the context, such as the project's credentials and what is being built.
2. **Give it one job in a short spoken brief.** The example brief a speaker gave on day 2 said the engineering bot will use pstack to spawn cloud agents to work on the game, and that its job is to orchestrate those agents, supervise them and check their work. It named the first phase, quick prototypes, and asked the bot-making bot not to make the engineer too focused on prototypes but durable enough for serious engineering work later.
3. **Ask for a restatement.** A speaker's favourite pattern is to end the brief with "Restate this in your own words before you start working", so you can confirm the bot understood a big blob of dictated text.
4. **Give it context and a home for it.** On day 1, a speaker told the engineering bot to spin up a cloud project, a kind of cloud agent suited to long work, to keep track of the application's engineering context, and to send more messages to that project whenever it needed engineering work done. The speaker wasn't sure it would stick with the project.
5. **Add a reviewer when you stop reading.** When the chief of staff bot opened a 2,000-line pull request by mistake, the speaker said they would not read all of it and planned a reviewer bot alongside the engineering bot.
6. **Rewrite the description as principles.** One speaker finds that agents tend to put all the details of a session into a rule or skill written right after a problem, which makes it less reusable. On day 2, when an engineering bot's description had become too specific, the speaker asked the bot-making bot to reread pstack's main skill and write principles to follow instead. The new description opened with one job: own engineering outcomes by orchestrating work through pstack and cloud agents, supervising and verifying. Asked for a view, another speaker said it looked good and was an improvement they could iterate on, though parts were "a little bit AI slop".

### A prompt to copy

> Create an engineering bot for me. Its job is to spawn cloud agents to work on <project>, orchestrate them, supervise them and check their work, not to write the code itself. For now we are <first phase>, but make it durable enough for serious engineering work later. Restate this in your own words before you start working.

## Signals and failure points

| What you notice | What it means | What to do |
|---|---|---|
| The bot writes code itself and stays busy | Its own context and computer are tied up | Tell it to spawn a cloud agent instead |
| It only handles the first phase well | Its brief was too narrow | Ask for a description durable enough for later work |
| A pull request is too big to read | No one reviews for you | Add a reviewer bot |
| Its description reads like a list of past incidents | Rules were written from single sessions | Rewrite it as principles |

An engineering bot set up this way stays a manager: it hands work to cloud agents, checks what comes back, and keeps a short description you can trust as the work grows.
