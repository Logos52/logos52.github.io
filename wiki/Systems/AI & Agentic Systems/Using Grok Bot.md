# Using Grok Bot

Day-to-day use, as shown across three public workshop days in mid-September 2026, is less about collecting more helpers and more about how you talk to the ones you already have. The orientation page covers what the product is. This page covers the loop you actually run.

Start by giving the helper a single duty and writing the hard limits into its profile, where you and anyone watching can see them. A slides helper on the first day carried rules for clean layout, type no smaller than 20 points, and a fixed set of colors. When those rules live only in a one-off prompt, they drift. When they live on the helper, you can audit them.

Ask in the thread for any job that should repeat. On-screen help said recurring tasks are set up that way. A sample request called for a start-of-day file review that listed who edited what. Memory should make a stored preference come back the next time that kind of choice appears, the way a stored color preference reappeared in a design demo.

When the work hits a fork, do not bury the choice in a paragraph of prose. Lay out labeled options. The stage used a trio of choices. You could lock the present direction, keep iterating, or hold. If you pick lock, name who will build. The same shape appeared when a prototype needed an access gate, with choices that included team-only protection, an allowlist tied to existing accounts, or a password. The point was to make the decision visible, not to pick a vendor.

Build the artifact before you let it act on the world. One helper drafted a product spec and locked the markdown before engineering work began. Another built a form and was marked as not sending it. Support-style guidance on the second day blocked an outside message until a review passed. Treat sending, merging, and flipping infrastructure as separate moves from drafting.

Match the reply to your confidence. High confidence can answer from public material, while medium confidence should show its work. Low confidence, or an ambiguous ask, should come back to you. Public pages can be quoted. Internal policy can decide a question and should not be pasted into a place other people will see.

Keep a shared source of truth and notice when it breaks. Helpers on the second day were told to keep a common docs workspace current. When that workspace returned a missing-page error, the critique helper stalled in public. The honest next line is that the connection failed, not a fabricated stand-in for the missing page.

Watch the fleet while it works. An overlay counted how many helpers existed, how many messages had been sent, how many were working, and how many were active. Those counts climbed through the first day from the low teens into the high twenties. The useful habit is to glance at working versus idle, not to chase a higher total.

Scope the request the way you would write a short job description before you let the helper run. A later session warned that bloated context slows the work. If a job has two duties, it is already two jobs.

This loop is the usage page. The short rule list lives next door. The three-day public build, including what was shipped in front of the audience, lives on the event chronicle.

## Open questions

How would you phrase the next outbound draft so that sending it required a separate yes?
